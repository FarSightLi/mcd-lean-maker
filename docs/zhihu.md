## 发法

技术文先发成**知乎文章**，再拿文章精简版去回答相关问题，在回答末尾附上文章链接，这样能借到问题本身的流量：

- MCP 有哪些有意思的应用？
- 有哪些值得一看的 AI Agent / Skill 项目？
- 程序员节你们在做什么？

不要同一天把同一段内容贴到多个问题下，容易被判搬运。知乎对外链限流，正文里的 GitHub 链接最多放两处：开头和结尾。

图片在编辑器里拖进去上传，`【配图：xxx】` 处按文件名插入。

与掘金那篇的分工：掘金讲实现细节，知乎讲设计取舍（为什么这么做），内容不重复。

### 比赛背景

麦当劳中国 2025 年底上线了官方 MCP Server，AI 通过它可以查门店、查菜单、核价、下单。今年程序员节，麦当劳在 GitHub 官方账号下办了一场创意开发大赛，要求基于这套 MCP 开发 Skill，按项目的 GitHub Star 数排名。

比赛仓库：github.com/M-China/mcd-developer-innovation-challenge

我做的叫**麦麦减脂助手**，解决一个减脂期天天遇到的问题：巨无霸去掉酱，能少多少卡？

【配图：docs/promo/bigmac-compare.png】

答案是 136 卡，513 → 约 377 kcal（351–399）。

做这个项目时，大部分时间没花在调接口上，花在了几个设计取舍上。下面挨个说。

### 取舍一：热量和价格，不让大模型算

最省事的写法是把营养表丢给大模型，让它自己加减。我没这么做，理由有两条：

1. **大模型会算错，而且错得很自信。**热量差几十卡，用户分辨不出来，这种错误比答不上来更糟。
2. **算错了没法复现。**同一个问题问两次可能得到两个数，也没办法写测试。

所以最后的分工是：

- 大模型负责理解"去酱""别放芝士"这类说法，把它们映射成 MCP 返回的 modification code
- 数字全部交给 Python 脚本 `calc.py` 计算
- 价格只认 MCP `calculate-price` 接口的返回值

脚本部分目前有 80 个测试用例。

### 取舍二：数据不够准的时候，给区间

MCP 只提供整份商品的营养数据，不提供"一份巨无霸酱多少卡"。23 个配料项我只能自己推导：

- **能精确算的**：吉士汉堡包 294 − 汉堡包 248 = 一片吉士 46 kcal，两款商品只差这一片芝士
- **能借数据的**：中美同款配方对得上的，采用美国官网或 USDA 的单项数据
- **只能估的**：大部分酱料，按同类食材估算

23 项里能精确算的只有 1 项，估算的有 19 项。

这种情况下给一个精确的单值，等于假装很准。所以每个配料都存成区间 `[下限, 上限]`，去掉配料时往保守方向扣，保证真实值落在区间里。页面上的数字都标了"约"，同时给出区间和置信度。

【配图：docs/promo/truth.png】

我觉得这是 AI 应用里容易被忽略的一点：**不确定的地方要明说，不能让输出看起来很确定。**

### 取舍三：下单必须人来点头

`create-order` 是会花钱的操作。Skill 里写了一条硬规则：用户没明确说"确认"，AI 就不准调用这个接口。

下单前，AI 必须先出一张确认卡，列出门店、商品、去掉的配料、热量区间、优惠券、实付金额。用户中途换店、换商品、改配料，都要重新核价，重新出卡。一次确认只对应一单。

能动手的 Agent，权限边界要写死在流程里，不能指望大模型自觉。

### 取舍四：静态页不连接口，全部预计算

为了让大家不用申请 Token 也能体验，我做了一个纯静态网页，托管在 GitHub Pages 上，没有后端。

做法是构建时把所有结果提前算好：

- 一个商品有 n 个可去配料，就只有 2ⁿ 种组合。用二进制位表示每项去不去（**位掩码**），前端拨开关等于查表
- 推荐方案按 71 档预算 × 131 档热量上限，共 9301 个格子全部算好，去重后只有 132 套组合

【配图：docs/promo/plan.png】

拖滑块、拨开关都是查表，所以打开就能用。分享链接里只带一个 `mask` 数字，扫码就能还原同一份配料。

【配图：docs/share-card.png】
